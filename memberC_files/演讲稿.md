# 🏥 医疗 AI Agent 系统 — 演讲稿

---

## 第 1 页：封面（30 秒）

大家好，我们小组今天展示的是**医疗 AI Agent 系统**——面向心电图解读和心血管临床决策支持。

这个项目的核心问题是：**在垂直医疗领域，到底是"检索增强生成"更好，还是"监督微调"更好？** 我们通过构建三个并行的推理管道，用 RAGAS 框架做了系统性的对比评测。

---

## 第 2 页：项目背景（1 分钟）

先说一下项目背景。

我们对比了两条技术路线。

左边是 **RAG 路线**——检索增强生成。思路是：用一个比较大的模型，在回答问题时实时检索外部知识库，把检索到的文献作为上下文喂给模型。优点是不用训练，缺点是每次都要检索，而且大模型比较吃显存。

右边是 **SFT 路线**——监督微调。思路是：拿一个小模型，用大量领域数据去微调它，把医学知识"内化"到模型参数里。优点是推理快、省资源，缺点是需要准备训练数据。

我们的目标就是：**在这两条路线之间做一个公平公正的对比**，看看到底哪种方案在医疗场景下更靠谱。

---

## 第 3 页：系统架构（1.5 分钟）

这是我们整个系统的架构图。

从上到下分了四层。

最上面是**展示层**——用户可以通过 Gradio 网页界面提问，也可以通过命令行调用。评测结果用 Matplotlib 生成可视化图表。

第二层是**业务逻辑层**，核心是一个叫 MedicalAgentRunner 的统一调度器。它负责根据用户选择的模式，把问题分发到对应的管道去处理。同时这一层还有 RAGAS 评测引擎，负责计算 Faithfulness 和 Answer Relevancy 这些指标。

第三层是**工具层**，封装了两个核心工具。一个是 MedicalRAGTool，负责 FAISS 语义检索；另一个是 MedicalModelTool，负责调用微调后的模型做推理。

最下面是**基础设施层**，包括 FAISS 向量索引、BAAI 的 bge-m3 嵌入模型、DeepSeek-1.5B 基座模型加上 LoRA 适配器，以及 78,000 多条医疗问答语料。

这个四层架构的好处是**每一层职责清晰、可以独立替换**。比如想换个嵌入模型，只改工具层就行，上面的业务逻辑完全不受影响。

---

## 第 4 页：三管道对比设计（1.5 分钟）

这是我们最核心的设计——**三个并行评测管道**。

**管道 1：Pure RAG**。用的是 1.5B 的基础模型，加上 FAISS 检索。模型本身没有经过医疗微调，所有的医学知识都来自运行时检索到的文献。这个管道代表的是"纯检索"路线。

**管道 2：Pure SFT**。用的是经过 QLoRA 微调的 1.5B 模型。不做任何检索，完全靠模型参数里"记住"的医学知识来回答。这个管道代表的是"纯微调"路线。

**管道 3：Hybrid Agent**。这是最复杂的管道。它把微调模型和 RAG 检索结合起来，由 smolagents 框架里的 CodeAgent 来自主决定什么时候该检索、什么时候该直接推理。这个管道代表的是"取长补短"路线。

三个管道通过统一的 MedicalAgentRunner 来调度，用同一套 RAGAS 评测框架来打分。这样就保证了对比的**公平性**——同一批测试题、同一套评分标准。

---

## 第 5 页：成员 A 的工作——RAG 知识检索库（1 分钟）

现在介绍一下我们三个成员各自的贡献。

成员 A 负责的是 RAG 知识检索库。

他收集了 **78,000 多条医疗问答对**，覆盖了 6 大领域：基础心脏病学、跨模态 ECG 诊断、复杂疾病分析、风险评估、临床对话。

数据经过清洗去重之后，用 BAAI 的 bge-m3 模型做了文本嵌入，生成了 1024 维的向量，然后用 FAISS 的 IVF-Flat 算法构建了向量索引。

他还做了消融实验来确定最优参数。最后选定的是 chunk_size 等于 512 个词、overlap 等于 50 个词、top_k 返回 3 篇文献，F1 分数达到了 **0.86**。

在实际使用中，78,000 篇文档里做语义搜索，不到一秒钟就能出结果。

---

## 第 6 页：成员 B 的工作——模型微调（1 分钟）

成员 B 负责模型微调。

他选的是 DeepSeek-R1-Distill-Qwen-1.5B 作为基座模型，用了 4-bit 的 QLoRA 方法来微调。

这里要强调一下 QLoRA 的关键技术：NF4 量化加上 Double Quantization。这两个技术组合起来，把训练显存压到了**仅 5.6 GB**。这意味着什么？一张 8GB 的消费级显卡就能训练，根本不需要 A100 那种昂贵的专业卡。

训练数据是 10,000 条医疗问答，其中包含 2,000 条 Chain-of-Thought——也就是带推理过程的样本。

最终的 LoRA 权重只有 **71MB**，非常轻量。推理一次只要 5 秒钟左右，而且支持中英文混合的医疗问答。

---

## 第 7 页：成员 C 的工作——Agent 架构与评测（1.5 分钟）

我负责的是 Agent 架构和双轨评测。

具体来说做了三件事。

第一，**Agent 系统**。写了大约 2,700 行 Python 代码。tools.py 封装了两个核心工具——RAG 检索工具和模型推理工具。agent_core.py 实现了三个管道，用了 smolagents 的 CodeAgent 来做智能体编排。build_index.py 负责构建 FAISS 索引。

第二，**双轨评测框架**。test_dataset.py 从 78,000 条语料里面，用 MD5 哈希去重，排除了 SFT 训练集的 10,000 条样本，然后按 5 个领域分层抽样，提取了 150 条完全没被训练过的测试题。run_evaluation.py 跑三管道推理并计算 RAGAS 指标。analyze_results.py 生成可视化图表。

第三，**Gradio Web Demo**。一个全中文的简洁交互界面，支持 GPU 真机推理，三种模式可以自由切换，还预设了示例问题。

---

## 第 8 页：评测结果（2 分钟）

这一页是**最关键的结果**。

我们来看三个管道在 Faithfulness 和 Answer Relevancy 上的表现。

首先是 **Faithfulness**，也就是忠实度——模型的回答能不能被上下文支撑。

Pure SFT 拿了 **0.8673**，是最高的。Pure RAG 只有 0.5954。Hybrid Agent 夹在中间，0.6179。

这个差距非常大——Pure SFT 比 Pure RAG 高了 **45.6%**。

然后是 **Answer Relevancy**，也就是答案相关性——回答跟问题对得上吗。

三个管道表现比较接近，Pure RAG 略高一点，0.8744。Pure SFT 是 0.8602。

那么这里得出什么结论呢？

**第一条结论：知识"内化"比"检索"更可靠。** 微调让 1.5B 的小模型在忠实度上大幅超越了 RAG 方案。说明在垂直医疗领域，一个好的微调比任何检索策略都管用。

**第二条结论：Hybrid Agent 没有达到预期。** 我们本来以为"微调模型加上检索"会是最强的组合，但实际上它的 Faithfulness 只有 0.62，远低于纯微调的 0.87。我们分析原因可能是 Agent 在检索和推理之间的协调引入了不确定性，反而降低了忠实度。

**第三条结论：小模型微调，性价比最高。** 1.5B 参数、71MB 的 LoRA 权重、5.6GB 训练显存，就能在医疗领域达到最好的忠实度。

## 第 9 页：Web Demo（1 分钟）

这是我们的 Web Demo。

一个基于 Gradio 的简洁中文界面。用户输入医学问题，选择推理模式，点击分析就可以得到 AI 回答。

支持三种模式：混合智能体是默认推荐，纯 SFT 速度最快，纯 RAG 带文献检索。

Demo 页面里还直接展示了三管道的评测对比数据，包括 RAGAS 指标表、关键结论和测试集的领域分布。用户一边体验 AI 问答，一边就能看到量化的评测结果。

目前 Demo 已经部署在本地，用 NVIDIA RTX 3060 显卡做 GPU 推理，DeepSeek-1.5B 加上 4-bit 量化，首次加载大概一分钟，之后每次推理只需要几秒钟。

---

## 第 10 页：总结与展望（1 分钟）

最后总结三点。

**第一，小模型微调优于大模型检索。** 在我们的实验里，1.5B 微调模型在忠实度上以 0.87 对 0.60 的成绩完胜 RAG 方案。知识内化比检索更可靠。

**第二，QLoRA 大幅降低了训练门槛。** 仅需 5.6GB 显存，8GB 消费卡就能做医疗领域微调。这意味着个人开发者也能训练自己的垂直领域模型。

**第三，Agent 架构还有很大的优化空间。** 我们目前的 Hybrid Agent 并没有展现出"一加一大于二"的效果。未来可以通过更好的 Chain-of-Thought 数据、更精细的检索策略来提升。

未来的方向我们觉得有三个：一是用更大规模的 CoT 数据做微调，二是引入多模态——比如直接把心电图图像作为输入，三是在真实临床场景下做验证。

## 附：可能的 QA 问题

**Q1: 为什么 Hybrid Agent 效果不如 Pure SFT？**

我们的分析是，Agent 在做检索-推理协调时，可能会过度检索或在不恰当的时候调用工具。这导致最终答案的连贯性下降。另外，CodeAgent 生成的 Python 代码有时不够精准，也会影响最终效果。这是一个值得深入研究的点。

**Q2: 6GB 显存够用吗？**

对于 1.5B 的模型来说完全够用。我们的 Pipeline 2 只需要大约 2GB 显存，加上 RAG 的嵌入模型总共也不到 6GB。但如果想跑 7B 级别的模型，6GB 就不够了——我们实际测试过，即使是 4-bit 量化，7B 模型也装不进 6GB 显存。

**Q3: RAGAS 指标的计算可靠吗？**

RAGAS 的 Faithfulness 和 Answer Relevancy 是通过 LLM 来打分的，有一定的偏差。我们在代码里同时实现了启发式的 fallback 方法——用关键词重叠和医学术语密度来做近似计算。但最准确的方式还是用人来标注。150 条测试集的结果更多是展示评测框架的工作流程，而不是严格意义上的学术基准。

**Q4: 这个系统能用于真实临床吗？**

绝对不能。这是一个课程作业，训练数据是公开数据集，没有经过严格的临床验证。Demo 页面底部的免责声明也写清楚了——仅供教学演示，不可用于临床诊断。
