# 🏥 医疗 AI Agent 系统 — 演讲稿

## 第 1 页：封面（30 秒）

大家好，我们小组今天展示的是**医疗 AI Agent 系统**——面向心电图解读和心血管临床决策支持。

这个项目的核心问题是：**在垂直医疗领域，到底是"检索增强生成"更好，还是"监督微调"更好？** 我们通过构建三个并行的推理管道，用 RAGAS 框架做了系统性的对比评测。

---

## 第 2 页：项目背景（1 分钟）

先说一下项目背景。

我们对比了两条技术路线。

左边是 **RAG 路线**——检索增强生成。思路是：用一个模型，在回答问题时实时检索外部知识库，把检索到的文献作为上下文喂给模型。优点是不用训练、知识可以随时更新，缺点是检索质量决定答案质量。

右边是 **SFT 路线**——监督微调。思路是：拿一个小模型，用大量领域数据去微调它，把医学知识"内化"到模型参数里。优点是推理快、省资源，缺点是需要准备高质量的训练数据。

我们的目标就是：**在这两条路线之间做一个公平公正的对比**，看看到底哪种方案在医疗场景下更靠谱。

---

## 第 3 页：系统架构（1.5 分钟）

这是我们整个系统的架构图。

从上到下分了四层。

最上面是**展示层**——用户可以通过 Gradio 网页界面提问，也可以通过命令行调用。评测结果用 Matplotlib 生成可视化图表。

第二层是**业务逻辑层**，核心是一个叫 MedicalAgentRunner 的统一调度器。它负责根据用户选择的模式，把问题分发到对应的管道去处理。同时这一层还有 RAGAS 评测引擎，负责计算 Faithfulness 和 Answer Relevancy 这些指标。

第三层是**工具层**，封装了两个核心工具。一个是 MedicalRAGTool，负责 FAISS 语义检索；另一个是 MedicalModelTool，负责调用微调后的模型做推理。

最下面是**基础设施层**，包括 FAISS 向量索引、BAAI 的 bge-m3 嵌入模型、DeepSeek-1.5B 基座模型加上 LoRA 适配器，以及 78,000 多条医疗问答语料。

这个四层架构的好处是**每一层职责清晰、可以独立替换**。比如想换个嵌入模型，只改工具层就行，上面的业务逻辑完全不受影响。

---

## 第 4 页：三管道对比设计（1.5 分钟）

这是我们最核心的设计——**三个并行评测管道**。

**管道 1：Pure RAG**。用的是 1.5B 的基础模型，加上 FAISS 检索。模型本身没有经过医疗微调，所有的医学知识都来自运行时检索到的文献。这个管道代表的是"纯检索"路线。

**管道 2：Pure SFT**。用的是经过 QLoRA 微调的 1.5B 模型。不做任何检索，完全靠模型参数里"记住"的医学知识来回答。这个管道代表的是"纯微调"路线。

**管道 3：Hybrid Agent**。这是最复杂的管道。它把微调模型和 RAG 检索结合起来，由 smolagents 框架里的 CodeAgent 来自主决定什么时候该检索、什么时候该直接推理。Agent 会生成 Python 代码来调用工具，像一个真正的智能体一样工作。这个管道代表的是"取长补短"路线。

三个管道通过统一的 MedicalAgentRunner 来调度，用同一套 RAGAS 评测框架来打分。这样就保证了对比的**公平性**——同一批测试题、同一套评分标准。

---

## 第 5 页：成员 A —— RAG 知识检索库（1 分钟）

现在介绍一下我们三个成员各自的贡献。

成员 A 负责的是 RAG 知识检索库。

他收集了 **78,000 多条医疗问答对**，覆盖了 6 大领域：基础心脏病学、跨模态 ECG 诊断、复杂疾病分析、风险评估、临床对话。

数据经过清洗去重之后，用 BAAI 的 bge-m3 模型做了文本嵌入，生成了 1024 维的向量，然后用 FAISS 的 IVF-Flat 算法构建了向量索引。

他还做了消融实验来确定最优参数。最后选定的是 chunk_size 等于 512 个词、overlap 等于 50 个词、top_k 返回 3 篇文献，F1 分数达到了 **0.86**。

在实际使用中，78,000 篇文档里做语义搜索，不到一秒钟就能出结果。

---

## 第 6 页：成员 B —— 模型微调（1 分钟）

成员 B 负责模型微调。

他选的是 DeepSeek-R1-Distill-Qwen-1.5B 作为基座模型，用了 4-bit 的 QLoRA 方法来微调。

这里要强调一下 QLoRA 的关键技术：NF4 量化加上 Double Quantization。这两个技术组合起来，把训练显存压到了**仅 5.6 GB**。这意味着什么？一张 8GB 的消费级显卡就能训练，根本不需要 A100 那种昂贵的专业卡。

训练数据是 10,000 条医疗问答，其中包含 2,000 条 Chain-of-Thought——也就是带推理过程的样本。

最终的 LoRA 权重只有 **71MB**，非常轻量。推理一次只要 5 秒钟左右。

---

## 第 7 页：成员 C —— Agent 架构（1 分钟）

我负责的是 Agent 架构、评测框架和 Web Demo。

先说 Agent 系统。写了大约 2,700 行 Python 代码。tools.py 封装了两个核心工具——MedicalRAGTool 负责 FAISS 语义检索，MedicalModelTool 负责调用微调模型做推理。两个工具都支持懒加载，首次调用时才初始化模型，避免不必要的显存占用。

agent_core.py 实现了三个管道的完整逻辑。Pipeline 3 的 Hybrid Agent 用了 smolagents 的 CodeAgent 范式——Agent 自主决策，输出 Python 代码来调用工具。如果 smolagents 不可用，还有一个基于规则的 fallback 方案。

build_index.py 负责从 78,000 条语料构建 FAISS 索引，用了 FP16 加速和文本截断优化。

## 第 8 页：评测怎么做的？（2 分钟）★ 重点

这一页我详细讲一下**我们是怎么评测 Agent 的效果的**。这是整个项目最有技术含量的部分。

### 第一步：准备测试集

评测的第一步是准备测试数据，这里最关键的是**保证测试集没有被模型"见过"**。如果拿训练过的数据来测试，那就不是评测，是作弊。

具体怎么做呢？

我们从成员 A 的 78,136 条语料出发。首先加载成员 B 的 SFT 训练集，提取出里面 10,000 条样本的用户问题，对每个问题做 MD5 哈希。然后在 78,136 条语料里面，凡是哈希匹配上的统统排除掉。

接下来做**分层抽样**。我们定义了 5 个医学领域：基础心脏病学、跨模态 ECG 诊断、复杂疾病分析、风险评估、临床对话。每个领域按比例抽取，最终得到 150 条测试题，每个领域各占 20%。

这样一来，150 条测试题**百分之百没有被训练过**，评测的公平性就有了保证。

### 第二步：选择评测指标

我们选了两个 RAGAS 的核心指标。

**Faithfulness，忠实度。** 这个指标衡量的是：模型的回答能不能从给定的上下文中推断出来？简单说就是——模型有没有在"编造"信息。如果模型说"患者需要立即 PCI 手术"，但检索到的文献里根本没提 PCI，那忠实度就低。这个指标对 RAG 管道尤其重要，因为你不能比检索到的文献说的更多。

**Answer Relevancy，答案相关性。** 这个指标衡量的是：回答跟问题对得上吗？模型有没有跑题？比如你问"房颤怎么诊断"，模型却回答了一大段房颤的药物治疗，虽然内容没错，但跟问题不相关，分数就会低。

### 第三步：跑评测

每个测试样本，我们把它同时喂给三个管道。

管道 1 会先做 FAISS 检索拿到 3 篇文献，然后把文献作为上下文，由基础模型生成回答。

管道 2 不做检索，直接由微调模型生成回答。注意管道 2 没有检索上下文，所以它的 Faithfulness 是用标准答案作为代理上下文来计算的——这其实对它不太公平，但至少有个参照。

管道 3 由 CodeAgent 自主决定——是先检索文献，还是直接推理，还是两者结合。

每个管道跑完生成答案后，RAGAS 计算两个指标，同时记录推理耗时。

### 第四步：结果分析

150 条样本跑完后，我们按管道聚合，计算每个指标的平均值、最小值、最大值。analyze_results.py 生成四张可视化图表——柱状图对比、雷达图、各领域细分图、时间质量散点图。

整个评测框架有个特点：**即使没有 GPU，也能在 demo 模式下跑通整套流程**。我们用启发式方法——关键词重叠、医学术语密度——来做近似计算，这样可以独立验证框架的正确性。

---

## 第 9 页：评测结果（1.5 分钟）

好，现在我们看结果。

首先看 **Faithfulness，忠实度**。

Pure SFT 拿了 **0.8673**，是最高的。Pure RAG 只有 0.5954。Hybrid Agent 夹在中间，0.6179。

这个差距非常大——Pure SFT 比 Pure RAG 高了 **45.6%**。这意味着在忠实度这个维度上，微调方案完胜检索方案。

然后看 **Answer Relevancy，答案相关性**。

三个管道表现比较接近。Pure RAG 最高，0.8744。Pure SFT 是 0.8602。Hybrid Agent 是 0.8364。

我解读一下这个结果。

**第一条结论：知识"内化"比"检索"更可靠。** 微调让 1.5B 的小模型在忠实度上大幅超越了 RAG 方案。这说明在垂直医疗领域，把你需要的知识在训练时"烧进"模型参数里，比运行时去检索要靠谱得多。

**第二条结论：Hybrid Agent 没有达到预期。** 我们本来以为"微调模型加上检索"会是最强的组合，但实际上它的 Faithfulness 只有 0.62，远低于纯微调的 0.87。我们分析原因可能是 Agent 在检索和推理之间的协调引入了不确定性——有时候检索了不相关的文献，有时候在不需要检索的时候也去检索，反而干扰了模型的判断。

**第三条结论：性价比极高。** 1.5B 参数、71MB 的 LoRA 权重、5.6GB 训练显存——这在 AI 领域是非常非常低的门槛。但就是这样一个"小模型"，在医疗领域的忠实度做到了 0.87。

## 第 11 页：总结与展望（1 分钟）

最后总结三点。

**第一，小模型微调优于大模型检索。** 准确说，在我们的实验里，"微调"这个操作本身比"检索"对答案质量的提升更大。知识内化比检索更可靠。

**第二，QLoRA 大幅降低了训练门槛。** 仅需 5.6GB 显存，8GB 消费卡就能做医疗领域微调。个人开发者也能训练自己的垂直领域模型，这是非常有意义的。

**第三，评测方法论很重要。** 我们建立了一套完整的评测流程——从测试集提取、去重、分层抽样，到三管道并行推理、RAGAS 指标计算、可视化分析。这套流程不仅适用于这个项目，也可以复用到其他垂直领域的 AI Agent 评测。

未来方向三个：一是更大规模的 CoT 微调数据，二是多模态——比如直接把心电图图像作为输入，三是在真实临床场景下做验证。

## 附：可能的 QA 问题

**Q1: 为什么 Hybrid Agent 效果不如 Pure SFT？**

我们的分析是，Agent 在做检索-推理协调时，可能会过度检索或在不恰当的时候调用工具，导致上下文噪音增加。另外 smolagents 的 CodeAgent 生成的 Python 代码有时不够精准——比如把问题直接翻译成英文去做检索，导致检索结果和原始问题的语义产生偏差。这是一个值得深入研究的点。

**Q2: Faithfulness 是怎么算出来的？**

RAGAS 的 Faithfulness 原理是：先把模型回答拆成多个独立的陈述句（claims），然后逐条检查每个陈述能不能从检索到的上下文中推断出来。比如回答里说"这是急性前壁心梗"，就去检查检索文献里有没有提到 ST 段抬高、V1-V4、前壁梗死这些关键信息。能推断出来的陈述越多，Faithfulness 就越高。我们在代码里也实现了一个启发式 fallback——用关键词重叠率来做近似计算。

**Q3: 150 条测试集够吗？**

对于课程项目来说是足够的，而且我们特别注重了数据的代表性和公平性——按 5 个领域做分层抽样，每条都确认没有被训练过。但如果是严谨的学术研究，150 条确实偏少，一般建议至少 500-1000 条。不过我们的评测框架设计是**可扩展的**，换更大测试集只需要改一个参数。

**Q4: 6GB 显存够用吗？**

对于 1.5B 的模型完全够用。Pipeline 2 只需要约 2GB 显存，加上 RAG 总共约 4GB。但 7B 模型即使 4-bit 量化也超过 6GB——我们实际测试过，Qwen2-7B 4-bit 加载需要约 5.5GB，加上 FAISS 和嵌入模型就不够了。这也是为什么我们最终统一用 1.5B 做基准对比。

**Q5: 这个系统能用于真实临床吗？**

绝对不能。训练数据是公开数据集，没有经过严格的临床验证和伦理审查。Demo 页面也写清楚了——仅供教学演示，不可用于临床诊断。真要做临床部署，需要经过临床试验、药监局审批、数据安全认证等一系列流程。
